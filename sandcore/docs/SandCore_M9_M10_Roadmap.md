# SandCore 后续里程碑要求（M9 / M10）

> 本文只规定目标、方向与约束，不预先锁定具体实现。
>
> **硬性要求：任何具体技术方案、数据结构、ABI/KMI 变更、磁盘格式、调度策略、权限模型、驱动模型、协议实现等，在正式开工前必须先向 mio 说明可选方案、影响与取舍，并等待 mio 决策。不得自行把重大设计选择直接写进系统。**

---

## 总体原则

- 持续推进 SandCore，但保持“简化实现、直击原理”的设计风格。
- **用户态组件优化是长期最高优先级之一**，不能只堆内核能力。
- 新增底层能力后，应尽可能提供实际可用的用户态接口、工具或应用。
- 保持现有扩展性，避免为了新功能破坏旧软件。
- `SCAPI.H` 当前继续采用 **只加不改** 原则：
  - 已公开 syscall 编号不改。
  - 已公开参数/返回语义不改。
  - 已公开结构布局尽量不改。
  - 新能力通过新增接口扩展。
- 后续可增加 `stdio.h`、`stdlib.h`、`string.h` 等标准/类标准用户态运行库，但是否加入、如何实现，必须先讨论。
- 长期目标之一：让更多第三方 C 软件、解释器、编译器、VM 等能够通过移植在 SandCore 上运行。

---

# M9

## 1. 持续优化用户态
- 继续完善 Shell、IDE、调试器、文件管理器、设置、图形程序等。
- 改善稳定性、易用性、一致性和实际可用程度。
- 新增底层能力时同步考虑用户态如何真正使用。
- 不允许系统逐渐变成“只有内核功能、没有成熟用户软件”的技术展示。

## 2. 声音系统
- 加入第一版声音能力。
- 用户态可以通过公开接口播放声音。
- 至少提供实际用户态程序验证声音系统。
- 保留后续继续扩展音频能力的空间。
- 具体硬件接口、缓冲机制、驱动结构、API 形式等开工前讨论。

## 3. 真正的多用户与权限管理
- 支持多个用户身份。
- 进程具有明确用户身份。
- 文件/目录开始具有权限与所有者概念。
- 系统目录与普通用户文件建立真实权限边界。
- 登录、用户环境、HOME 等逐渐成为真正的系统概念。
- UID/GID、rwx、ACL、capability 等具体模型开工前讨论。

## 4. `/SYS/MOD` 开始收紧
- 不再长期保持“普通程序写入后即可在下次启动获得 Ring 0”的宽松模型。
- 建立安装/写入内核模块所需的权限边界。
- 仍然保留第三方或用户扩展内核模块的能力。
- 具体权限、安装流程、信任模型在实现前讨论。

## 5. Ring 0 串口调试
- 加入可选串口内核调试能力。
- GUI、窗口系统甚至部分内核组件异常时，仍能观察内核状态。
- 可输出启动、异常、任务、模块、内存等调试信息。
- 作为后续 SMP、网络、驱动开发的重要基础设施。

## 6. 串口文件接收
- 支持宿主机向 SandCore 发送文件。
- 用于程序、资源、模块、测试文件快速传入。
- 降低频繁重新构建磁盘镜像的开发成本。
- 传输协议、校验和错误恢复方案开工前讨论。

## 7. 指令集 / 工具链能力继续扩展
- 扩展 S3C 可生成的 x86 指令。
- 扩展 assembler 支持。
- 补充必要 ABI / runtime 能力。
- 为移植更复杂 C 软件和其他运行时做准备。
- 保持已有 S3C 自举能力与验证思想。

## 8. GPU 初步
- 开始加入 GPU / 图形硬件加速相关基础。
- 建立“用户态 → 图形接口 → 驱动/内核 → GPU/设备”的真实路径。
- M9 不要求一步实现复杂现代 3D API。
- GPU 模型、设备、指令和命令提交方式开工前讨论。

# M10

## 1. 正式网络通信
- 加入真正的网络能力。
- 支持网络设备、基础协议、用户态网络接口。
- 用户程序可以与真实外部设备通信。
- 为浏览器和联网软件提供基础。
- 协议栈范围、网络 API、驱动设备等按阶段讨论后实现。

## 2. 中文与输入法
- 尝试加入中文输入能力。
- 逐步建立 Unicode / UTF-8、中文字体、输入法组合状态、候选与提交机制。
- 用户态文本控件能够真正接收中文输入。
- 第一版范围与输入法方案开工前决定。

## 3. 小型浏览器
- 实现一个真正使用 SandCore 网络栈的小型浏览器。
- 能访问网页、解析并显示基础网页内容。
- 与 SandCore GUI、输入、字体、网络真正集成。
- 不预先要求达到现代 Chrome/Firefox 的复杂度。
- HTML/CSS/JS 支持范围必须先讨论。

## 4. `/SYS/CORE` 签名校验
- `/SYS/CORE` 中核心 SKM 在进入 Ring 0 前进行真实性/完整性验证。
- 建立更清晰的核心信任边界。
- 为稳定系统更新机制打基础。
- 签名算法、密钥模型、信任根和失败处理必须先讨论。

## 5. `/SYS/CORE` 作为长期系统扩展机制
- 保持较小、稳定的基础 kernel。
- 后续大量系统能力尽量通过新增或更新 `/SYS/CORE/*.SKM` 提供。
- 尽量减少为了新增功能反复修改基础 kernel。
- 保持 SKM 扩展机制长期可演进。
- 不适合模块化的能力不强制模块化，边界后续讨论。

## 6. SCAPI / 用户态兼容性继续演进
- `SCAPI.H` 保持“只加不改”。
- 新功能可新增 SCAPI 接口。
- 不因内核内部改成 SKM 就破坏已有 Ring 3 应用。
- 后续可增加标准 C 运行库层，让第三方程序减少对 `SCAPI.H` 的直接依赖。
- 逐渐让 SandCore 成为真正的 C target platform。

# M10 SMP / 多核路线

## 总目标
- 支持真正 SMP。
- 内核从单 CPU 假设演进为可安全处理多个逻辑处理器并发执行。
- 最终至少验证到 **16 个 logical processors**。
- “16 个”指逻辑处理器数量，不等同于 16 个物理核心。
- 后续可进一步识别物理核心、SMT/超线程等 CPU topology。

## M10a
- 首先稳定支持 2 个逻辑处理器。
- 建立真正 SMP 所需的基础结构。
- 两个 CPU 最终能够同时执行不同 Ring 3 任务。
- 代码结构不能只写死“永远只有两个 CPU”，应为后续扩展保留结构。
- AP 启动、同步、锁、APIC、调度等具体方案开工前讨论。

## 后续 M10 子版本
逐步验证和优化：
- 2 logical CPUs
- 4 logical CPUs
- 8 logical CPUs
- 16 logical CPUs

随着数量增加，逐步处理：
- per-CPU 状态
- 跨核同步
- 调度扩展
- CPU affinity
- task migration
- load balancing
- IPI
- TLB 一致性
- 锁竞争
- CPU topology
- SMT / 超线程关系

每阶段具体加入哪些机制，由实际问题和测试结果决定，不提前写死。

# 第三方软件与语言生态

SandCore 后续应逐渐提高标准 C 软件兼容性。

方向包括：
- 完善 C 语言能力。
- 增加标准/类标准头文件和运行库。
- 完善文件、内存、时间、进程、网络等基础能力。
- 尝试移植并非专门为 SandCore 编写的真实 C 项目。
- 后续可尝试移植由 C/C++ 实现的：
  - 解释器
  - 编译器
  - VM
  - 数据库
  - 压缩/图像库
  - 游戏
  - 其他运行时
- 如果成功移植一个语言运行时，则允许其上层语言生态开始进入 SandCore。

具体首批移植项目不在本文锁定。

---

# 长期方向

SandCore 长期逐渐形成：
- 稳定用户态 ABI。
- 可演进用户态 API。
- 更标准的 C 运行环境。
- 自托管工具链。
- 成熟用户态软件。
- 多用户与权限模型。
- 可加载且受信任控制的内核模块。
- 声音、GPU、网络等设备能力。
- SMP 多核执行。
- Unicode / 中文输入。
- 浏览器与网络应用。
- 第三方软件移植能力。
- 长期可扩展的软件平台。

# 开发决策规则

1. **本文只定义目标，不授权 Agent 自行决定重大实现方案。**
2. 每进入一个新的大功能前，先检查当前源码和已有设计。
3. 开工前必须向 mio 说明：
   - 当前状态。
   - 要解决的问题。
   - 可选实现。
   - 各方案的优缺点。
   - 对兼容性和后续架构的影响。
4. **等待 mio 明确选择或批准后，再正式实现。**
5. 不允许为了赶进度擅自破坏现有 ABI、格式、模块接口或用户态兼容性。
6. 每个里程碑完成后必须：
   - 总结做了什么。
   - 说明为什么这样做。
   - 给出验证结果。
   - 说明已知限制与技术债。
   - 提出下一步选项。
   - 再等待 mio 决策。

> **SandCore 的开发方式本身也是项目的一部分：AI 负责分析、实现与验证，但关键架构方向始终由 mio 决策。**
