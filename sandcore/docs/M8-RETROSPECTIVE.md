# M8 复盘：真彩色成立，复杂软件 3D 需要先评估

作者 **mio**，2026-10-04。依据用户本次封存决定和已经存在的测量整理经验，不追加构建、渲染或 QEMU 测试。状态以 [M8-FROZEN.md](M8-FROZEN.md) 为准。

用户对收束的最新评价是：**目前已经够用，而且很优秀，只是部分未完成。** 本文复盘的是未达到预期的高成本图形路线与立项方法，不否定本版本已经有用的主体成果。

## 1. 应当留下的判断

真彩色输出和复杂 3D 内容必须分开评估。RGB/ARGB32、原生清晰文字、透明图标、窗口/主题和工具组件已经形成有用成果，用户本次明确认可。颜色深度扩充本身，不要求每个像素都发射几何/阴影/反射射线。

困难集中在当前 **纯软件、整数、逐像素三维查询和着色** 的设计，加上 SCCC 生成代码、单核客体执行、内存/帧提交和虚拟化后端。游戏高 CPU 的现场测量中确有大量用户态计算；较早 Monitor 鼠标移动的无效整帧重绘和旧游戏合成成本也有独立证据，不能把所有 100% 都归成同一个原因。

这说明当前架构与本轮“接近现代、原生高清、丰富实时光影和流畅”目标不匹配，**不能据此证明 CPU 3D 一律不可行，也不能断言加上 AVX/FPU/SIMD 就能解决**。新增指令能力、GPU 或混合渲染须先做兼容合同、分项成本和真实收益评估。本机 Intel GPU 渲染影片成功不等于 SandCore 已有 GPU 驱动。

## 2. 有价值的改进与未成功的路线

| 经验 | 实际依据 | 今后怎么使用 |
|---|---|---|
| 无效工作应先消除 | Monitor 只在按钮 hover 外观变化时重画，鼠标移动客体忙碌由原约 87% 降到后轮约 2%；完整条件见 PERFORMANCE.md | 静止控件/菜单不能因任意坐标更新而整帧工作；保留拖动、边沿、焦点与数据更新 |
| 输入和长复制不能互相阻塞 | 大帧复制保持可信当前任务/CR3并开放 IRQ，真实输入/像素/活动关闭回收通过 | 从设计开始给输入队列、调度、复制和退出明确时序，而不是最后补“感觉不卡” |
| 局部合成、批量内存操作有用 | 高分辨率损伤区域、旧索引按行处理、SCMEM/REP和相应独立护栏/像素等价证据 | 使用正确裁剪/整数放大/缓存失效；不能靠减少真实显示内容得到成绩 |
| 固定精度整数热路有真实成本 | 宽点积、整数 DIV、SCCC 简单表达式后端有完整整数/副作用/callee/三代收敛证据 | 保留通用库与正确性夹具；算法层仍须降低查询数量，不能仅靠更快乘法期待几十倍游戏收益 |
| 结构正确不等于更快 | SCVOX 8 格块索引六图正确，但两轮中位成本旧 91/88、新 125/139 PIT，默认接入已撤回 | 空间索引必须包含维护、空区跳跃收益和实际场景分布；失败源及成本也是资产 |
| 测试不能掩盖中间错误 | Race 每物件 reset 曾掩盖累计 17 次近地平线阴影范围越界；诊断后保守粗筛修复并保持完整像素 | 每次操作的错误需累计观察；最终 error=0 不能覆盖此前错误，粗筛要证明不会漏真实遮挡 |
| 后端/负载会改变数字 | 同 World 的 TCG/WHPX持续输入调用计数约 1.25/11.9；不同轮固定提交 28/65 亦伴随 PIT 与负载变化 | 对照须绑定源码、SCX、像素、后端和宿主状态；不能拼不同轮数字作为算法收益 |
| 高样本预算也需要设计 | 旧影片固定 512 样本预计多天，新自适应候选真实 4K 单帧 14～26 秒但画质对照未完成 | 先分析误差/难像素和视觉差异，再设采样/去噪预算；不机械对所有背景像素付同样成本 |

所有数值只对应原证据条件。没有因此宣布所有组件丝滑、游戏可玩或画质已达到顶级要求。

## 3. 本轮设计和执行需要改进的地方

1. **性能可行性门槛放得太晚。** 在完整现代游戏画质承诺前，应已量到正式 SCCC 产物在指定客体/后端下的真实预算，而不是依据宿主 CPU 强、算法能写出来就推测能流畅。
2. **把颜色升级、桌面打磨、编译器和现代软件三维揉进了同一交付承诺。** 它们成本和风险差异很大；以后应先给每类工作独立边界、性能预算和可审阅的画面设计，再约定整版范围。
3. **小夹具证明不了整机体验。** 数学值、六张小图和严格回收十分重要，但不能作为完整高清游戏 FPS、输入延迟、现代画质和玩法流程的替代。以后每个代表场景应尽早跑完整尺寸。
4. **同像素微优化无法替代渲染架构选择。** 当前每像素多层求交、阴影与反射很贵；应先比较可见面/几何批处理、增量扫描、合理空间组织、正确失效的预生成材质/静态光照及 GPU 候选的成本，再选择路线。这里记录候选思路，不声称已实现这些后续架构。
5. **整片启动前没有得到足够可靠的时长与画质预算。** 需要覆盖最贵玻璃/反射镜头和连续真实帧，确认噪点、去噪、运镜及编码/系统播放空间。仅完成一张漂亮图不应直接承担 2520 帧队列成本。

## 4. 后续立项前的评估清单

以下是将来提出方案时的门槛；本次不自动启动实验或下一版本。

1. **写清目标和排版。** 分别列工具/游戏/动画的真实画布尺寸、像素密度、视觉参考、界面和场景布局、光照/玩法规模；明确可审阅的设计，不用功能数量替代美感。
2. **绑定运行环境。** 记录正式编译器/SCX、CPU/虚拟化后端、内存和显示设备；测最小呈现成本、典型场景和最坏场景，区分客体 PIT、宿主时间、提交调用和真实显示帧。
3. **分项预算。** 60FPS 是整帧 16.67ms，30FPS 是 33.33ms，包含逻辑、场景更新、可见性、着色、复制/提交/合成；再记录 P50/P95/P99 与输入延迟。拿不到支持目标的预算，就应提出可审阅的架构或范围选择。
4. **代表场景先证明。** 正式编译器产物、真实分辨率、完整材质/光影、相同场景和输入交替测量；允许资源预生成时公开空间、失效、动态编辑/昼夜/相机变化正确性。
5. **再决定 GPU/新指令。** 做能力发现、资源所有权、任务隔离、上下文切换、异常/退出回收与无加速回退；保留旧 SCAPI.H API/ABI、VGA/PS2/ATA及历史程序。
6. **用户批准后才改范围或封存。** 性能困难时提交实际数据、排版/设计方案与可行选项，不由代理自行降低画质、删玩法或提前放弃。当前 M8 的封存有本次用户明确决定，不能拿它作为以后默认放弃的先例。
